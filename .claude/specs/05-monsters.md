# Монстры спецификация

Монстры — основной источник угрозы в игре. Игрок никогда не убивает монстра
обычным способом: главная защита — закрытые глаза, укрытия и свет. Механика
монстра строится вокруг одного принципа: игрок невидим, пока не смотрит.

**Код:** `Source/MyCharacters/Public|Private/` — `ABaseMonster`, `AEnemyAIController`
(устарел, не используется), компоненты `UMonsterAudioComponent`,
`UMountRiderComponent` (на стороне персонажа).  
**Ассеты:** `BP_TestMonster`, `ABP_Whisper` (AnimBP), монтажи атаки с Anim Notify.  
**Документы-источники:** `combat-stealth-rules-DRAFT.md`,
`implementation-roadmap.md` (Фазы 0–6), `docs/demo-story.md`.

## 1. Цель

Монстры создают постоянное напряжение через асимметричные правила: монстр
не видит игрока с закрытыми глазами, но при малейшей ошибке запускает
каскад, из которого сложно выбраться. Цель архитектуры — единая базовая
модель угрозы (`ABaseMonster`) с точечными флагами для особых типов, без
разветвлённой иерархии классов.

## 2. Терминология

| Термин | Значение |
|---|---|
| **Эпизод** | Одна «сессия угрозы» от первого обнаружения до разрешения (смерть или успешный уворот всех монстров). Сбрасывается вместе с `bHasMissedPanicStrikeThisEpisode`. |
| **Раздражение / Scanning** | Состояние монстра после промаха: `EnterScanningState()`, `CheckForPlayer()` заморожен, монстр не атакует повторно. |
| **Орда / волна** | Все живые монстры локации, ещё не выбывшие из текущего эпизода, реагирующие на `BroadcastAlert()`. |
| **Выбыл из эпизода** | Монстр промахнулся → `bHasMissedPanicStrikeThisEpisode = true` → больше не участвует в орде текущего эпизода. |
| **Точка первой поимки** | Фиксированная координата, куда идут монстры орды. Не живая позиция игрока. |
| **crouch-dodge** | Уворот: игрок **и** присел **и** закрыл глаза в момент удара. |
| **BlindEncounterMonster** | Ссылка на монстра, с которым сейчас активен слепой физический контакт. При `OpenEyes()` — мгновенная смерть. |
| **bIsLit** | Флаг горения `AHolyItem` (свеча/кадило). Потушенный предмет не даёт защиту. |

## 3. Структура кода и ассетов

```
Source/MyCharacters/
  Public/
    ABaseMonster.h              — базовый класс всех монстров
    Components/
      UMonsterAudioComponent.h  — звук монстра (стон, дыхание, рычание, удар)
  Private/
    ABaseMonster.cpp
    Components/
      UMonsterAudioComponent.cpp

Content/
  Blueprints/
    BP_TestMonster              — тестовый BP-наследник ABaseMonster
  Animations/
    ABP_Whisper                 — AnimBP монстра (State Machine: Idle/Walk/Attack)
```

**Ключевые методы `ABaseMonster`:**

| Метод | Роль |
|---|---|
| `CheckForPlayer()` | Основной тик-опрос; заморожен в Scanning/Panic/Ridden |
| `TryStartChaseAttack()` | Угроза от открытых глаз (Фаза 1.1) |
| `TryStartNaskokAttack()` | Угроза от физического наскока (Фаза 1.2a) |
| `TryStartPanicStrike()` | Удар орды по лежащему игроку (Фаза 1.2d) |
| `PunishRepeatProvocation()` | Мгновенный удар при повторной провокации в Scanning |
| `BroadcastAlert()` | Зов всех монстров локации к точке первой поимки |
| `EnterScanningState()` | Раздражённое сканирование после промаха |
| `RequestMoveToActor()` / `RequestMoveToLocation()` | Единственные точки входа для AI-движения (все 9 старых вызовов через них) |
| `ApplyKnockback()` | Физический отброс (свеча/молитва/Потолочный монстр) |
| `IsLocationProtected()` | Находится ли точка в защитной зоне света |
| `IsTargetInLight()` | Находится ли цель в зоне защиты |
| `ReactToProbe()` | Косметический разворот при прощупывании (G) |

## 4. Недочёты, допущения, важно

**Важно:** `ABaseMonster` — God-класс. Новую логику класть только если она
намертво привязана к уже существующему коду внутри. Всё остальное — в отдельный
компонент.

**Важно:** Два независимых пути смерти. Не путать:
- Через здоровье: `ChaseAttackDamage` накапливается → `HandleDeath()` при 0.
- Мгновенное убийство (Blind Encounter): `OpenEyes()` при валидном
  `BlindEncounterMonster` → `ResolveBlindEncounterKill()`, минуя здоровье.

**Важно:** `BroadcastAlert()` исключает самого себя (`OtherMonster == this`).
Поэтому при попадании монстр-инициатор сам явно ищет обратный путь к цели через
`RequestMoveToLocation()`, если оказался вне `CatchDistance` после knockback-а паники.

**Допущение:** Карта — не открытый мир. На локации фиксированный, заранее
известный набор монстров. Орда не порождает новых монстров, только активирует уже
существующих.

**Допущение:** Монстр не может честно преследовать игрока с закрытыми глазами —
он не знает текущую позицию. Поэтому орда идёт к **фиксированной** точке первой
поимки, а не к `GetActorLocation()` игрока.

**Недочёт:** При одновременном попадании двух монстров индикатор паники на HUD
завис на мёртвом теле. Нужен guard `bIsDead` на обновление HUD-индикатора паники.

**Недочёт:** Ретрай-циклы поиска тени монстром (`«wander point search FAILED —
retrying»` в `BaseMonster.cpp`) — работает на тестовой геометрии, наблюдать
на сложной.

**Недочёт:** `AEnemyAIController` — несвязанный неиспользуемый класс (мёртвый код).
Удалить при удобном случае.

## 5. Состояния ИИ

Почему это нужно: монстр должен быть предсказуем по правилам, но опасен по
исполнению. Четыре состояния дают игроку понятную модель поведения противника.

```
        ┌──────────────────────────────┐
        │           PATROL             │◄─────────────────────────┐
        │  ходит по маршруту           │                          │
        └──────────┬───────────────────┘                          │
                   │ видит открытые глаза                         │ промах → ScanDuration истёк
                   ▼                                              │
        ┌──────────────────────────────┐                          │
        │           CHASE              │                    ┌─────┴──────────────┐
        │  преследует, зовёт подмогу   │   промах (crouch)  │     SCANNING       │
        │  BroadcastAlert()            ├───────────────────►│  CheckForPlayer()  │
        └──────────┬───────────────────┘                    │  заморожен         │
                   │ достал (CatchDistance)                  └─────────────────── ┘
                   ▼
        ┌──────────────────────────────┐
        │           STALK              │
        │  у края защитного света      │
        │  не завершает атаку          │
        └──────────────────────────────┘
```

| Переход | Условие |
|---|---|
| Patrol → Chase | Открытые глаза в `SightDistance` и поле зрения |
| Chase → Scanning | crouch-dodge (присел + закрыл глаза) |
| Chase → Stalk | Игрок вошёл в защитный конус света |
| Scanning → Patrol | `ScanDuration` истёк, игрок не выдал себя |
| Scanning → удар | Игрок выдал себя в окне Scanning (повторный контакт/открыл глаза) |

## 6. Обнаружение игрока

Почему это нужно: закрытые глаза — базовая защита игрока и центральная механика
игры. Без чёткой модели обнаружения правила становятся непрозрачными.

**Текущая реализация (бинарная):**

```
IsEyesClosed() == true  →  монстр не видит (независимо от дистанции)
IsEyesClosed() == false →  SightDistance + угол зрения → Chase
```

**Дополнительные факторы защиты:**
- `UHidingComponent` (укрытие) — гарантированная безопасность, монстр не ищет.
- Защитный свет (`IsLocationProtected`) — монстр переходит в Stalk.

> ⏳ **Планируемая полная система видимости (Фаза 1.1b):** видимость как сумма
> факторов (тёмная одежда + сажа на лице + закрытые глаза), масштабирующих
> `SightDistance`. В коде не реализовано. Старт — после решения об источнике
> одежды/сажи.

## 7. Схема угрозы — полный цикл

Почему это нужно: несколько независимых источников угрозы (открытые глаза,
наскок, прощупывание) переиспользуют одну инфраструктуру разрешения удара.
Это позволяет добавлять новые триггеры без копирования логики.

### 7.1 Угроза от открытых глаз (`TryStartChaseAttack`)

```
Открытые глаза в зоне видимости
  → BroadcastAlert()
  → Chase → второй BroadcastAlert() перед ударом
  → TryStartChaseAttack()
      ├─ crouch-dodge → промах → EnterScanningState()
      └─ нет уклонения → ChaseAttackDamage + EnterPanicState()
```

### 7.2 Угроза от наскока (`TryStartNaskokAttack`)

```
Физический контакт капсул (наскок/прогулка/прыжок)
  ├─ Первый раз:
  │     ├─ присел → промах → ReactToProbe() [разворот 1.5с] → Patrol
  │     └─ не присел → попадание → урон + паника + BroadcastAlert()
  └─ Повтор пока монстр развёрнут или в Scanning:
        → PunishRepeatProvocation() [мгновенный удар без шанса]
```

### 7.3 Прощупывание вручную (`UProbeComponent`, клавиша G)

Горизонтальный трейс в приседе на 800 юнитов:

```
Монстр не раздражён → рычание + разворот (ReactToProbe(), 1.5с)
  └─ повторное нажатие пока стоит развёрнутым → PunishRepeatProvocation()

Монстр в Scanning за этим игроком → PunishRepeatProvocation()
```

### 7.4 Разрешение удара (единая таблица)

| Состояние в момент удара | Результат |
|---|---|
| **Присел И закрыл глаза** (crouch-dodge) | Промах → `EnterScanningState()` |
| Присел, глаза открыты | Гарантированный урон → орда |
| Только глаза закрыты (без приседа) | Гарантированный урон → орда |
| **Лежит в панике, глаза закрыты** | Промах → монстр выбывает |
| Лежит в панике, глаза открыты | Смерть (`OnKillPlayer`) |
| Встал после паники (стоя), глаза закрыты | Уворот нужен полный crouch-dodge |
| **Верхом на монстре** | Сброс (`OnKnockedOffMount`) + урон, БЕЗ паники |

> Правило приседа при панике отличается: пока `bIsPanicking == true`, достаточно
> только закрытых глаз (персонаж физически лежит, нажимать «присед» поверх не
> нужно). Как только встал (`RecoverFromKnockdown`) — снова нужен полный crouch-dodge.

## 8. Призыв орды

Почему это нужно: единственный монстр не создаёт достаточного давления после
первого укуса. Орда делает каждое попадание экспоненциально опасным, пока
игрок сам не прервёт цикл уворотом.

```
Гарантированный урон
  → BroadcastAlert()
  → Все монстры локации, не выбывшие из эпизода,
    идут к точке первой поимки
  → Каждый делает одну попытку:
      ├─ Промах → bHasMissedPanicStrikeThisEpisode = true
      │           монстр НАВСЕГДА выбывает из эпизода
      └─ Попадание → новый BroadcastAlert() + тут же бьёт снова
```

**Гашение волн:** искусственного лимита нет. Монстры выбывают по одному
при каждом промахе. Правило монстра-инициатора — `PanicStrikeEligibleTime`:
даже если он один на карте, получает право вернуться в цикл после паузы
(`PanicStrikeRearmDelay`).

**Почему точка фиксированная, не живая:** монстр не может знать, куда убежал
игрок с закрытыми глазами. Живая погоня (`RequestMoveToActor`) была реализована
как промежуточный вариант и откачена — противоречит базовому правилу.

## 9. Паника

Почему это нужно: паника — ключевое напряжение игры. Упасть ещё не значит
умереть, но любая ошибка в этот момент летальна. Мини-игра даёт окно для
спасения, делая каждый инцидент интерактивным.

```
EnterPanicState()
  → PlayKnockdownAnimation() [bIsPanicking = true]
  → Мини-игра дыхания (Space в такт носом)
        ├─ Глаза закрыты → удары орды промахиваются
        ├─ Глаза открыты + орда попала → OnKillPlayer() [смерть]
        ├─ OpenEyes() вручную → мгновенная смерть (BlindEncounterMonster)
        ├─ WASD во время паники → PanicMeter += PanicMovementPenalty (30f)
        ├─ PanicMeter достиг максимума → ForceEyesOpenFromPanic()
        │     → FindNearbyMonster(MonsterProximityKillRadius)
        │           есть монстр → смерть; нет → повезло
        └─ Успех → bIsAwaitingGetUp = true
                    → «Вперёд» (W) → RecoverFromKnockdown()
                      вернуться в позу до удара (стоя/присед)
```

**Убранный таймер:** старый «умер сам по себе через N секунд» — удалён.
Смерть исключительно от реального удара орды или открытия глаз.

**Наказание за движение:** edge-triggered по каждому направлению W/A/S/D
отдельно, не по удержанию. Суммирование при одновременном нажатии нескольких
направлений — не происходит.

## 10. Защитные зоны (свет)

Почему это нужно: свет — активный инструмент, а не просто декорация. Монстр
должен уважать свет и реагировать на него предсказуемо.

| Метод | Источник | Эффект на монстра |
|---|---|---|
| `IsLocationInProtectionCone()` | Свеча Священника | Монстр → Stalk, не завершает атаку |
| `CheckAuraProximity()` | Свеча (аура) / Кадило | Оглушающий урон (`UCandleDamageType`, `ApplyStun()`); кадило верхом — физический толчок (`CenserPushbackForce`) |
| `IsProtectedByHeldItem()` | Кадило (AI-решение) | Монстр держится у края, не атакует |
| `TryScatterPrayer()` | Молитва Священника (X) | `ApplyKnockback()` + `UCandleDamageType` на всех в радиусе 500 |
| `TryHolyExplosion()` | Взрыв Наездницы (X) | Гарантированное убийство всех в радиусе 500 |

**Правило `bIsLit`:** все три источника щита (толчок ауры / взмах / AI-Stalk)
синхронно отключаются при `bIsLit == false`. Потушенный предмет не защищает.

**Наскок в край щита:** `OnCapsuleHit()` проверяет `IsTargetInLight(Player)`
перед `TryStartNaskokAttack()`. Монстр не бьёт игрока, который стоит в своей
же зоне защиты.

## 11. Реакция на окружение

Почему это нужно: монстры живут в том же мире, что и игрок. День/ночь и
ловушки должны влиять на обоих.

### 11.1 День/ночь (`ADayNightManager`)

- **День:** монстры разбегаются в тень. На открытом пространстве — к зданиям,
  на закрытом — в буквальную тень. Сгорание при отсутствии тени — валидный исход.
- **Триггеры:** `OnDawnStarted` / `OnDayStarted` / `OnNightStarted`.

### 11.2 Капкан (`ABearTrap`)

- Игрок пешком → QTE освобождения (15 нажатий E), скорость упала.
- Монтированный монстр наступает → замирает на `RiddenMonsterHoldDuration`=3с →
  сбрасывает Наездницу → капкан уничтожается.

## 12. Взаимодействие с героями

Почему это нужно: каждый герой влияет на монстров по-разному. Это формирует
уникальное ощущение от каждого персонажа и делает выбор героя значимым.

### 12.1 Реднек
- **Таран (Rage Dash):** физическое столкновение станит монстра, выбрасывает на свет.
- **Баф самогона:** `SetImmuneToMonsterAttacks(true)` — монстры видят
  (зовут подкрепление, гонятся), но не могут нанести урон/панику во время бафа.
- **Похмелье-запах** (`ScentDuration`=6с): `BroadcastAlert()` периодически
  (`ScentPulseInterval`=1.5с) после окончания бафа.
- **Пьяный НПС-приманка** (`ADrunkNPCSpawner`): монстры, зашедшие на зов,
  замораживаются `DisableMovement()` на рассчитанное время.

### 12.2 Священник
- **Конус свечи** → Stalk (не завершает атаку).
- **Аура свечи** → оглушение + периодический урон.
- **Раскидывание молитвой (X)** → `ApplyKnockback()` на всех в радиусе 500,
  кулдаун 20с, ресурс не тратится.

### 12.3 Наездница
- **Монтирование (F):** монстр полностью под управлением игрока
  (`bIsBeingRidden = true`). Удар по верховому → сброс без паники.
- **Кадило верхом:** полный радиус + толчок. На ногах — уменьшенный радиус
  (`FootProtectionRadius`=180), атака по ногам раз в `LegSwipeCooldown`=3с
  (50% шанс), без паники.
- **Святой взрыв (X):** убийство всех в радиусе 500, бак гасится, требует ≥5 топлива.

### 12.4 Брат ⏳

- В форме монстра — рядовые монстры не атакуют («свой»).
- Трансформация — не `ABaseMonster`, отдельная форма `ABrotherCharacter`.
- Звук-приманка: привлекает рядовых монстров к себе, освобождая путь Сестре.
- **Исключение:** Потолочный монстр атакует Брата даже в форме.

## 13. Особые типы монстров

Почему это нужно: единая базовая модель хороша для большинства монстров,
но отдельные сюжетные и геймплейные моменты требуют исключений из базовых
правил — чтобы удивить игрока и сломать его устоявшуюся модель безопасного
поведения.

---

### 13.1 Монстр с хоботом-присоской (Акт I)

Нарративный монстр пролога. Вводит игрока в механику свечи.

### 13.2 Монстр тоннеля — «атакует при закрытых глазах» (Акт VII) ⏳

Ломает центральное правило игры: закрытые глаза больше не защищают.
Впервые появляется в тоннеле, делая его первым по-настоящему страшным участком.

| Атрибут | Значение |
|---|---|
| Флаг | `bIgnoresClosedEyes` — **не реализован** |
| Атака при закрытых глазах | Да — `IsEyesClosed()` игнорируется |
| При попадании | `ForceEyesOpenFromPanic()` → принудительное открытие глаз |
| Результат | Отбрасывание → паника → подтягиваются другие монстры |

**Требование к коду:** в `CheckForPlayer()` добавить ветку:
если `bIgnoresClosedEyes == true` — не проверять `IsEyesClosed()`,
сразу `TryStartChaseAttack()`.

**Цепочка при встрече:**
```
Монстр замечает → атака (игнорирует закрытые глаза)
  → ForceEyesOpenFromPanic() → EnterPanicState()
  → BroadcastAlert() → орда подтягивается
  → Успех мини-игры → бег к укрытию (расчёт дистанции)
  → Провал → смерть
```

### 13.4 Потолочный монстр ⏳ (Фаза 6, п.18)

Вертикальная угроза, ломающая ещё одно базовое правило: против него не помогают
ни закрытые глаза, ни трансформация Брата. Единственное спасение — укрытие.

**Жёсткая зависимость:** код не начинать до готовности Фазы 7 (трансформация
Брата) — нужна проверка «Брат в форме», чтобы убедиться, что монстр его всё
равно атакует.

| Атрибут | Значение |
|---|---|
| Обнаружение | Видит при **любом** состоянии глаз — исключение из `IsEyesClosed()` |
| Движение | По потолку/стенам; по полу — прыжками |
| Убить | Нельзя (даже Наездница); только `ApplyKnockback()` отбросить |
| Брат в форме | Единственный, кто его атакует — не считает «своим» |
| Спасение | Только `UHidingComponent`/`AHidingSpot`; вентиляция — не безопасна |

**Поведение при поимке:**
```
Удар → ApplyKnockback() [далеко] + BroadcastAlert()
  Отброс = окно для побега/поиска укрытия, не чистое наказание.
  Повторная поимка ДО укрытия → критический урон (~50% здоровья)
```

**Появление — две параллельные системы триггера:**
- Точки дизайнера (для конкретных сюжетных моментов).
- Рандомный механизм в подходящих местах (для непредсказуемости).
- Перед появлением — нарастающий звук (честное окно на поиск укрытия).

**Навигация — три варианта (не выбрано, решить на прототипе):**
- (а) Кратчайший путь + переориентация по нормали ближайшей поверхности.
- (б) По расставленным дизайнером точкам/сплайнам.
- (в) Процедурная навигация по произвольным поверхностям пол/стена/потолок.

## 14. Размерные категории ⏳

Почему это нужно: монстры разного размера должны иметь разные параметры без
дублирования C++-классов — через конфигурацию, не наследование.

Реализация — `UDataAsset` (Фаза 6, п.15).

| Параметр категории | Описание |
|---|---|
| Скорость | `MaxWalkSpeed` и скорость Chase |
| Зона поражения | `CatchDistance`, `ChaseAttackDamage` |
| `bCanBeMounted` | Можно ли оседлать (Наездница) |

## 15. Звуковое сопровождение (`UMonsterAudioComponent`)

Почему это нужно: игра рассчитана на игру в темноте — игрок физически не видит
монстров, только слышит. Звук — основной инструмент ориентирования и предупреждения
об угрозе.

Компонент создаётся в конструкторе каждого монстра. `ABaseMonster.cpp` не тронут
(только одна строка в конструкторе).

| Звук | Условие воспроизведения | Настройка |
|---|---|---|
| Фоновый стон | Всегда, 3D-спатиализация | Автоматическое затухание по дистанции |
| Дыхание | Игрок в `BreathingProximityRadius` | ≈ `CatchDistance` = 150 |
| Рычание | `IsScanningForPlayer()` == true | Пока монстр раздражён |
| Звук удара | Anim Notify на монтаже атаки | `PlayAttackHitSound()` — ручной шаг в редакторе |

Звуковые ассеты назначаются в Blueprint defaults вручную.
