# Общие техники персонажей — спецификация

Общие для (почти) всех героев техники взаимодействия с правилом «монстр не видит
вслепую»: открытие/закрытие глаз, паника после первого удара монстра (вынужденное
закрытие глаз с мини-игрой дыхания), прощупывание пространства вслепую, эффект
темноты с закрытыми глазами и укрытие в предмете. Это «фундамент», на котором каждый
конкретный герой (`01-priest-character.md`, `02-redneck-character.md`,
`03-rider-character.md`, `04-brother-sibling.md`) строит собственную уникальную
технику «видения вслепую».

Код расположен в `Source/MyCharacters/Public/BaseCharacter.h` /
`Source/MyCharacters/Private/BaseCharacter.cpp` (глаза, Eye Peek, паника/дыхание),
`Source/MyCharacters/Public/Components/ProbeComponent.h` /
`.../Private/ProbeComponent.cpp` (прощупывание), а также `UHidingComponent` /
`AHidingSpot` (укрытие). Персонаж-специфичные техники закрытых глаз живут в
собственных компонентах каждого героя (`UVisionFireSourceComponent`,
`UFingerFlamePeekComponent`, `UInkVisionComponent`, `UHunterFocusComponent`) и
перечислены здесь только как ссылки — подробности в их собственных спецификациях.
Правила детектирования монстрами и разрешения ударов (`ABaseMonster::IsPlayerVisible()`,
`TryStartPanicStrike()`, `PunishRepeatProvocation()` и т.д.) подробно описаны в
`05-monsters.md` — эта спецификация на них ссылается, а не дублирует.

## 1. Цель

Почему это нужно: все четыре героя (включая дуэт Брат/Сестра) играют вокруг одного
общего правила — «монстр не видит игрока с закрытыми глазами, но игрок тогда и сам
почти ничего не видит». Чтобы это правило ощущалось честно и единообразно на любом
герое, базовые действия — открыть/закрыть глаза, спрятаться — реализованы один раз в
`ABaseCharacter` и переиспользуются всеми подклассами. Поверх этой общей базы каждый
герой получает **свою** технику компенсации слепоты — так персонажи остаются
различимыми, не теряя общей честной основы.

## 2. Терминология

| Термин | Значение |
|---|---|
| **bIsEyesClosed** | Базовый флаг закрытых глаз (`ABaseCharacter`); `true` — экран затемнён, монстры не видят через обычную видимость |
| **IsEyesClosed()** | `bIsEyesClosed \|\| bIsBlindedByAbility` — то, что реально проверяют монстры и игровая логика |
| **bIsBlindedByAbility** | Флаг «слепой по способности» (`SetBlindedByAbility()`) — тот же эффект на детекцию, что и `bIsEyesClosed`, но без мини-игры дыхания и без мгновенной смерти при «открытии» (использует Чернильное зрение Наездницы) |
| **Eye Peek / Подглядывание** | Третий, независимый канал обнаружения: игрок удерживает ПКМ (`bIsAiming`) — видит сквозь полуприкрытые веки (виньетка + лёгкое DoF), но остаётся уязвим, если попадает в конус зрения монстра |
| **Blind Encounter** | Физический слепой контакт с монстром (`BlindEncounterMonster`); произвольное `OpenEyes()` в этот момент — безусловная мгновенная смерть |
| **ForceEyesOpen / SetEyesLockedOpen / SetEyesLockedClosed** | Недобровольные/заблокированные состояния глаз — используются способностями (например, баф самогона Реднека), не самим игроком напрямую |
| **EyesClosedPostProcessComp** | Пост-процесс базового затемнения экрана при закрытых глазах; подавляется флагом `bIsDarknessSuppressedByAbility`, когда поверх него должен быть виден собственный эффект способности (Огонёк, Воспалённое зрение, Чернильное зрение) |
| **UHidingComponent** | Универсальный компонент укрытия, есть у каждого героя (создаётся в конструкторе `ABaseCharacter`, как `UInventoryComponent`/`UProbeComponent`) |
| **AHidingSpot** | Мировой предмет-укрытие (шкаф/ящик/бочка), в который прячется `UHidingComponent` |
| **Силуэт монстра (не реализовано)** | Расплывчатый, «дёргающийся» визуальный образ монстра, который должен быть виден в темноте закрытых глаз в рамках персонажных техник (см. §8) |
| **Паника (bIsPanicking)** | Вынужденное состояние после первого удара монстра: персонаж сбит с ног, движение WASD заблокировано, запущена мини-игра дыхания. Третье, непроизвольное состояние глаз — в отличие от §5–6, здесь персонаж не выбирает открыть/закрыть глаза сам, а должен успеть зажмуриться и удержать ритм дыхания |
| **PanicMeter / «сердцебиение»** | `[0, PanicMeterMax]` — концептуально «уровень сердцебиения»: 0 — полностью успокоился (`EndPanicSafely()`), максимум — паника на пике, глаза распахиваются сами (`ForceEyesOpenFromPanic()`) |
| **Мини-игра дыхания (ритм-дыхание)** | `Space` в такт носом: `OnBreathPressed()` в окне `BreathToleranceWindow` вокруг `NextBreathBeatTime` — успех снижает `PanicMeter` (`RegisterNoseBreath()`), промах/ртом повышает (`RegisterMouthGasp()`). Визуально на HUD — два сходящихся круга (индикатор ритма, `GetBreathBeatProximity()`), отсюда бытовое описание «совместить круги» |
| **bIsAwaitingGetUp** | Дыхание выровнено (`PanicMeter == 0`), персонаж ещё физически лежит и ждёт либо нажатия «вперёд» (встать, `RecoverFromKnockdown()`), либо прощупывания (G) |
| **«Добивание лежащего» (piling on)** | Второй (и далее) удар орды по уже лежащему/ожидающему подъёма персонажу (`TryStartPanicStrike()`); решает исход закрытость глаз в момент удара — закрыты → промах и монстр выбывает из эпизода, открыты → смерть |
| **Прощупывание (UProbeComponent, G)** | Действие вслепую: горизонтальный трейс вперёд на `ProbeRange`, сообщает «свободно» / «монстр впереди» / «стена», не открывая глаз |
| **Повторная провокация (PunishRepeatProvocation)** | Второе прощупывание (или физический контакт) уже насторожённого этим же игроком монстра — мгновенный удар без шанса на уворот |
| **PanicMovementPenalty** | Штраф к `PanicMeter` (30f) за попытку сдвинуться (WASD) во время паники — edge-triggered по каждому направлению отдельно, не по удержанию; суммирование при одновременном нажатии нескольких направлений не происходит |

## 4. Недочёты, допущения, важно

**Важно:** открытие/закрытие глаз, Eye Peek и укрытие реализованы **один раз** в
`ABaseCharacter`/`UHidingComponent` и не дублируются по героям. Любая будущая правка
этих базовых механизмов затрагивает всех героев сразу — трогать их тела без явной
причины запрещено (`CLAUDE.md`, правило 2).

**Допущение:** формулировка «открытие глаз привлекает монстров в радиусе N» — это
упрощённое концептуальное описание. Фактическая модель обнаружения не является чистым
радиусом: это дальность зрения (`SightDistance`) **и** угол поля зрения монстра **и**
отсутствие препятствий (см. `05-monsters.md` §6, §7.1). «Радиус N» ближе всего к
радиусу оповещения орды (`BroadcastAlert()`/`AlertRadius`), который срабатывает уже
**после** первого обнаружения, а не к самому первичному обнаружению. Разграничение
зафиксировано в §5 ниже.

**Недочёт:** общая система рендера силуэтов монстров с закрытыми глазами (§8) — **не
реализована**. Это единственная система, которую ждут сразу три персонажных
техники: Огонёк на пальцах Священника (силуэты не рисуются вообще), Mental Trail
Реднека (маркеры задавлены затемнением экрана с 27.08.2026), и частично Чернильное
зрение Наездницы (есть собственный `M_InkVision`, но без «дёргания»/фантомных
образов, описанных в §8). Эта спецификация формализует **целевое** поведение системы;
имплементация — отдельная будущая задача.

**Открытый вопрос:** техника «подглядывание» Реднека (упомянутая в
`implementation-roadmap.md` как его способ видеть вслепую) технически — это
переиспользование **общего** Eye Peek (ПКМ, `bIsAiming`), усиленного Охотничьим
глазомером (`UHunterFocusComponent`). В отличие от Священника/Наездницы у него нет
безопасной выделенной способности «видеть не открывая глаз» — его риск того же рода,
что и у общего Eye Peek для любого героя. Зафиксировать явно при постановке ТЗ, не
путать с «ещё не определённой дополнительной техникой» — по состоянию на сегодня
дополнительной техники сверх Eye Peek + Глазомер не описано.

**Открытый вопрос:** техника закрытых глаз для Брата и Сестры не определена — дуэт
является особым персонажем (управляется поочерёдно, с переносом одного на плечах
другого), и его техника передвижения/видения вслепую не сформулирована. См.
`04-brother-sibling.md` §7.1 (зрение в монстр-форме Брата — вариант Чернильного
зрения, цвет не определён) и §12 (открытые вопросы дуэта).

**Допущение:** «укрытие достаточно под размер персонажа» (ограничение по размеру
предмета относительно персонажа) — **не реализовано**. Текущий код (`UHidingComponent::
TryToggle()`) ищет ближайший свободный `AHidingSpot` в радиусе `HidingSpotSearchRadius`
без какой-либо проверки совместимости размеров персонажа и укрытия — укрытие
безусловно подходит любому герою. Разграничение по размеру — будущая задача, см. §9.

**Важно:** укрытие (`UHidingComponent`) — **полностью отдельное** состояние, не
переиспользует систему закрытых глаз: `bIsEyesClosed` не трогается при входе/выходе
из укрытия. Спрятавшийся персонаж невидим независимо от состояния глаз.

**Недочёт:** прощупывание (`UProbeComponent::Probe()`) требует `IsCrouched() == true`
и отдельно блокируется, пока `bIsPanicking == true`. Окно, когда дыхание уже
выровнено, но персонаж ещё лежит (`bIsAwaitingGetUp`), технически снимает только
блокировку по панике — `IsCrouched()` при этом отражает присед **до** падения
(`Crouch()`/`UnCrouch()` не вызываются автоматически ни при нокдауне, ни при подъёме).
Если персонаж не был в приседе в момент удара, прощупывание в этом окне не сработает,
хотя по дизайну («преодолел панику → можно подняться или начать прощупывание») должно
быть доступно всегда. Исправление — либо явно приседать в `EnterPanicState()`, либо
убрать проверку `IsCrouched()` для состояния `bIsAwaitingGetUp` отдельно.

**Открытый вопрос:** доступность «подглядывания» (Eye Peek, ПКМ) Реднека во время
паники — `Tick()` принудительно обнуляет `bIsAiming`, пока `bIsPanicking == true`
(см. §7.4), то есть пока персонаж лежит, у Реднека нет вообще никакой техники
видения вслепую, кроме самого ритма дыхания. Не решено ни получит ли он отдельную
«паническую» альтернативу, ни — если жёсткую блокировку всё же решат ослабить —
будет ли сам быстрый взгляд лёжа смертельным исходом по умолчанию, или обычным
риском Eye Peek, как и вне паники.

**Открытый вопрос:** поведение паники для Брата и Сестры не определено вообще — ни
для кого из двоих не описано, что происходит при первом ударе монстра (дуэт
управляется поочерёдно, один несёт другого на плечах) — см. §7.4 и `04-siblings.md`.

**Недочёт (перенесено из `05-monsters.md`):** при одновременном попадании двух
монстров индикатор паники на HUD (`UPlayerHUDWidget`) завис на мёртвом теле. Нужен
guard `bIsDead` на обновление HUD-индикатора паники.

## 5. Открытие глаз

Почему это нужно: закрытые глаза — базовая защита игрока. Открытие глаз — обратная
сторона: оно даёт обзор, но жертвует главной защитой. Правило должно быть понятным и
последовательным для всех героев одинаково.

**Базовый механизм:**

```
IsEyesClosed() == false (глаза открыты)
  → ABaseMonster::IsPlayerVisible(): монстр, у которого игрок в SightDistance
    И в угле поля зрения И без препятствий на линии видимости → обнаруживает игрока
  → TryStartChaseAttack() — см. 05-monsters.md §7.1
```

Концептуально («в радиусе N монстры замечают персонажа») это описание верно как
упрощение, но фактическая дальность — это **конус** (дистанция + угол), не окружность;
см. допущение в §4.

**Каскад после первого обнаружения** (подробности — `05-monsters.md` §7–8):
```
Монстр заметил игрока (открытые глаза, в конусе)
  → BroadcastAlert() — оповещает ВСЮ орду в радиусе AlertRadius
  → вся орда идёт к фиксированной точке первой поимки
```
Именно здесь появляется настоящий «радиус» — но это радиус оповещения орды уже
**после** обнаружения, а не механизм самого обнаружения.

**Пути открытия глаз:**

| Способ | Функция | Произвольность |
|---|---|---|
| Игрок сам нажал Shift (тоггл) | `ToggleEyesClosed()` → `OpenEyes()` | Да — мгновенная смерть, если в этот момент идёт Blind Encounter |
| Способность форсирует открытие | `ForceEyesOpen()` (например, баф самогона Реднека) | Нет — без проверки Blind Encounter/мгновенной смерти |
| Паника доходит до максимума | `ForceEyesOpenFromPanic()` | Нет — отдельная проверка близости монстра, см. §7 и `05-monsters.md` §9 |
| Подглядывание (ПКМ) | `bIsAiming` (Eye Peek) | Формально глаза остаются «закрытыми» (`bIsEyesClosed` не меняется), но третий канал обнаружения (`TryTriggerEyePeekEncounter()`) всё равно может поймать игрока |

**Блокировки:** `SetEyesLockedOpen(true)` блокирует `CloseEyes()` (глаза нельзя закрыть,
пока способность держит их открытыми); `SetEyesLockedClosed(true)` — зеркально
блокирует добровольное `OpenEyes()`.

## 6. Закрытие глаз — база и персонажные техники

Почему это нужно: закрытые глаза — единственная гарантированная защита от обычной
видимости монстра, но полная слепота без компенсации сделала бы игру неиграбельной.
Поэтому у каждого героя есть собственная техника «увидеть, не открывая глаз» — со
своим балансом риска.

**База (общая для всех):**

```
Shift → ToggleEyesClosed()
  bIsEyesClosed: false → true → CloseEyes(): экран темнеет (EyesClosedPostProcessComp)
  bIsEyesClosed: true → false → OpenEyes(): см. §5 (в т.ч. проверка Blind Encounter)
```

Пока `bIsEyesClosed == true`:
- Монстры не видят игрока через обычную видимость (`IsPlayerVisible()`/
  `IsPlayerLookingAtMonster()`) — независимо от дистанции.
- Экран затемнён базовым пост-процессом, если его не подавляет персонажная
  способность (`SetEyesClosedDarknessSuppressed()`).

**Персонажные техники поверх базы** (детали — в соответствующих спецификациях,
здесь только ссылка и роль):

| Персонаж | Техника | Безопасность | Спецификация |
|---|---|---|---|
| Священник | Огонёк на пальцах (F, 5с/5с) + Воспалённое зрение (V, режим от первого лица) | Полностью безопасна — `bIsEyesClosed` не трогается, обнаружение не меняется | `01-priest-character.md` §9–10 |
| Наездница | Чернильное зрение (V, 10с/15с) | Полностью безопасна — `SetBlindedByAbility(true)`, отдельный канал без риска открытия | `03-rider-character.md` §8 |
| Реднек | «Подглядывание» = общий Eye Peek (ПКМ) + Охотничий глазомер (слоу-мо, подсчёт шагов) | Рискованная — тот же канал обнаружения (Eye Peek Risk), что доступен любому герою; параметры не до конца определены, см. §4 | `02-redneck-character.md` §10 |
| Брат и Сестра | Не определена — особый дуэт с собственной механикой передвижения (перенос, вентиляция) | — | `04-brother-sibling.md` §7–9, §12 |

Общий принцип дизайна: у Священника и Наездницы — **безрисковая** компенсация слепоты
(разный визуальный язык, одна и та же гарантия необнаружения); у Реднека — та же
слепота, что у всех, но с выбором рискнуть подглядеть вместо гарантии.

## 7. Паника — третье, вынужденное состояние глаз

Почему это нужно: §5–6 описывают состояние глаз как **произвольный** выбор игрока.
Паника — обратный, навязанный случай: первый удар монстра не убивает сразу, а сбивает
персонажа с ног и запускает мини-игру, где именно состояние глаз (на этот раз не
выбранное спокойно, а вырванное стрессом) решает, выживет ли персонаж. Это то же
правило «монстр не видит вслепую», доведённое до предела напряжения — персонаж
буквально теряется монстром из виду, если успевает зажмуриться лёжа, но платит тем,
что сам почти ничего не видит, не может встать и должен совладать с паникующим
дыханием, прежде чем снова что-то решать.

Подробности разрешения ударов и призыва орды, завязанные на эту же механику, —
`05-monsters.md` §7.4, §8–9; здесь — обзор с точки зрения состояния персонажа.

### 7.1 Жизненный цикл: от первого удара до возвращения на ноги

```
Первый удар монстра (открытые глаза / наскок / Eye Peek / повторное прощупывание)
  → EnterPanicState(): персонаж падает (нокдаун-анимация), bIsPanicking = true,
    WASD заблокировано (камерой по-прежнему можно свободно крутить — см. §7.3)

  Персонаж ЗАКРЫЛ глаза (Shift) → монстр теряет его из виду, но остаётся рядом
    → мини-игра дыхания: повышенное «сердцебиение» (PanicMeter) растёт/падает
       каждый такт (BreathRhythmInterval):
         ├── Space нажат вовремя (нос, в такт) → PanicMeter снижается
         │     (визуально на HUD — два круга сходятся друг с другом, см. §2)
         ├── Space мимо такта или не нажат совсем (ртом) → PanicMeter растёт,
         │     монстров оповещает BroadcastAlert() (громкий вдох ртом слышен)
         ├── PanicMeter дошёл до 0 → дыхание выровнено, паника преодолена
         │     → bIsAwaitingGetUp = true → теперь можно либо встать (W),
         │       либо начать прощупывание (G, см. §7.2) — ПОКА глаза остаются
         │       закрытыми, не открывая их
         └── PanicMeter дошёл до максимума → сердцебиение на пике → глаза
               РАСПАХИВАЮТСЯ САМИ (ForceEyesOpenFromPanic(), непроизвольно) →
               монстр рядом (MonsterProximityKillRadius)? → смерть;
               никого рядом → повезло, персонаж поднимается сам

  Персонаж НЕ закрыл глаза (или глаза остаются открытыми всё это время)
    → монстр добивает лежащего вторым ударом (TryStartPanicStrike()) → смерть
```

**Правило «второй удар = смерть»** проявляется тут трижды, по одной и той же логике
«не успел зажмуриться/сбился — умер»:

| Источник второго удара | Условие выживания | Условие смерти |
|---|---|---|
| Добивание лёжа (piling on, `TryStartPanicStrike()`) | Глаза закрыты в момент удара → промах, монстр выбывает из эпизода | Глаза открыты (не закрыл после падения ИЛИ открыл добровольно) → `OnKillPlayer()` |
| Пик паники (`PanicMeter` = максимум) | Рядом нет монстра (`FindNearbyMonster()`) → повезло | Монстр в радиусе `MonsterProximityKillRadius` → смерть |
| Повторное прощупывание того же насторожённого монстра | — (мгновенный удар без шанса на уворот) | Всегда — `PunishRepeatProvocation()`, см. §7.2 |

**Убранный таймер:** персонаж не умирает «сам по себе» от долгого лежания — смерть
только от реального удара орды или от распахнувшихся на пике паники глаз
(`05-monsters.md` §9).

### 7.2 Прощупывание вслепую (`UProbeComponent`, клавиша G)

Почему это нужно: с закрытыми глазами (в панике или просто добровольно) персонаж не
видит, свободен ли путь впереди. Прощупывание — единственный способ проверить это,
не открывая глаз и не выдавая себя монстру, который пока не насторожен.

```
G нажата (требуется присед — IsCrouched(), см. недочёт в §4) →
  горизонтальный трейс вперёд на ProbeRange (800)
    ├── чисто впереди → «Впереди свободно»
    ├── монстр впереди, ещё НЕ насторожен → ReactToProbe():
    │     рычание + разворот монстра (ProbeStartleDuration = 1.5с)
    └── монстр уже насторожен ЭТИМ ЖЕ игроком (Scanning/Startled) →
          PunishRepeatProvocation(): мгновенный удар без шанса на уворот
            → EnterPanicState(), если ещё не в панике, либо прямое добивание,
              если уже лежит
```

**Прощупать одного и того же монстра дважды подряд, пока он насторожен —** всегда
второй, смертельно опасный удар: `PunishRepeatProvocation()` не даёт шанса на
уворот, в отличие от первого прощупывания (которое лишь спугивает монстра). Чтобы
прощупать снова безопасно, нужно дождаться, пока монстр потеряет фокус
(`EndProbeStartle()`/выход из Scanning).

### 7.3 Поворот и поиск пути во время паники

**Важно:** во время паники (`bIsPanicking`/`bIsAwaitingGetUp`) вращение камеры
(`Look()`, мышь/правый стик) **не блокируется и не штрафуется** — `PanicMovementPenalty`
начисляется только за новое нажатие WASD (попытку физически сдвинуться), не за поворот
обзора. Это даёт персонажу возможность, не вставая и не открывая глаз, осмотреться
(насколько это возможно вслепую — ориентируясь по звуку/прощупыванию) и спланировать,
в какую сторону вставать и двигаться, чтобы выйти из окружения монстрами, как только
подъём станет возможен.

### 7.4 Что видно с закрытыми глазами во время паники

Почему это нужно: просто закрытые глаза в панике дают персонажу то же самое базовое
восприятие, что и закрытые глаза вне паники — приблизительные, «дёргающиеся» силуэты
монстров (§8), не точную картину. У персонажа есть два альтернативных пути получить
больше информации, не открывая глаза по-настоящему: **либо** общий путь — прощупывание
(§7.2) вместе с силуэтами (§8), **либо** собственная персонажная техника видения
вслепую (§6). Это разные инструменты одного и того же назначения, а не слои одной
системы — персонаж полагается на тот или другой в зависимости от того, чем
располагает его герой и что уместно в моменте.

**Путь 1 — прощупывание в темноте с силуэтами (общий, не персонажный):** пока
`bIsEyesClosed == true` (в том числе во время мини-игры дыхания), действует то же
целевое поведение силуэтов, что описано в §8 — нечёткий, «дёргающийся» силуэт
монстра, который рядом (а он гарантированно рядом — иначе удар не состоялся бы), без
точной позиции. Как уже указано в §7.1–7.2, прощупывание (G) доступно и во время
паники тем же порядком, что и вне неё — как только дыхание выровнено
(`bIsAwaitingGetUp`), можно прощупать пространство вслепую, с тем же правилом
«второй раз по тому же насторожённому монстру — смертельный удар». Этот путь
одинаково доступен всем героям и не зависит от персонажной техники из таблицы ниже.

**Путь 2 — персонажная техника видения вслепую:**

| Персонаж | Техника видения вслепую в панике | Статус |
|---|---|---|
| Священник | Воспалённое зрение (`UVisionFireSourceComponent`) | Формально не блокируется паникой — использует то же `bIsEyesClosed`, которое персонаж обязан держать во время мини-игры дыхания в любом случае |
| Наездница | Чернильное зрение (`UInkVisionComponent`) | Формально не блокируется паникой — `SetBlindedByAbility(true)`, тот же канал, что и вне паники |
| Реднек | «Подглядывание» (общий Eye Peek, ПКМ) | **Открытый вопрос** — см. ниже |
| Брат и Сестра | — | **Не определено вообще** — см. ниже |

**Открытый вопрос (Реднек):** сейчас «подглядывание» во время паники принудительно
выключено — `Tick()` каждый кадр обнуляет `bIsAiming`, пока `bIsPanicking == true`
(чтобы нельзя было одновременно целиться/зумить камеру и играть в мини-игру дыхания,
и чтобы `TryHijackAttackPress()` Реднека не сработал лёжа). Не решено, должно ли это
оставаться жёсткой блокировкой, или Реднек должен иметь возможность рискнуть быстрым
взглядом лёжа (ценой открытых глаз в момент, когда рядом монстр, добивающий лежащего,
см. таблицу в §7.1) — то есть не определено, будет ли такой быстрый взгляд в режиме
паники/падения смертельным исходом сам по себе или просто обычным риском Eye Peek,
как и вне паники. До решения у Реднека в панике нет вообще никакой техники видения
вслепую сверх базовых силуэтов, кроме самого ритма дыхания.

**Открытый вопрос (все персонажные техники пути 2):** нужно ли «ухудшать» личную
технику видения вслепую именно во время паники по сравнению с обычным применением —
например, сокращать время действия (Воспалённое зрение/Чернильное зрение короче
обычных 5с/10с) или сужать поле зрения/радиус обзора, раз персонаж лежит и
оглушён паникой, а не стоит в спокойном осознанном состоянии. Сейчас обе техники
(Священник, Наездница) работают в панике с теми же параметрами, что и вне неё —
решить при постановке ТЗ, нужна ли разница вообще, и если да, то для каких именно
техник и в какой мере.

**Открытый вопрос (Брат и Сестра):** поведение дуэта во время паники **не определено
вообще** — ни для одного из двоих не описано, что происходит при первом ударе монстра
(дуэт управляется поочерёдно, один несёт другого на плечах — неясно, кто «падает», как
мини-игра дыхания и прощупывание применяются к паре, и что при этом происходит со
вторым персонажем дуэта), и тем более не определена для них отдельная техника
видения вслепую в панике поверх базовых силуэтов. См. `04-siblings.md`.

## 8. Темнота с закрытыми глазами — расплывчатые силуэты монстров

> ⏳ Не реализовано. Раздел формализует целевое поведение общей системы — см. §4.

Почему это нужно: полная чернота с закрытыми глазами не даёт игроку вообще никакой
информации о монстрах даже там, где персонажная техника (Огонёк, Воспалённое зрение,
Чернильное зрение, Глазомер/Mental Trail) должна её предоставлять. Нужен единый визуальный
язык «вижу вслепую» — специфичный для слепого восприятия, намеренно неточный, но не
бесполезный.

**Целевое поведение:**

```
Глаза закрыты (или эквивалент — bIsBlindedByAbility)
  Монстр находится в зоне, где персонаж «смотрел» бы, будь глаза открыты
    → на экране появляется нечёткий, размытый силуэт монстра
       ├── силуэт "дёргается": на миг виден в одной точке, с подрагиванием,
       │     затем перескакивает в другую — реальное положение монстра дано
       │     лишь очень приблизительно, не как точная позиция
       └── возможны фантомные образы — силуэты, которые появляются и пропадают:
             - при изменении угла обзора персонажа, и/или
             - просто по времени (таймер), независимо от реального монстра
```

**Назначение неточности:** силуэт — это намёк, не радар. Игрок ориентируется по
примерному направлению и факту присутствия угрозы, но не может точно прицелиться по
нему или точно просчитать безопасный маршрут — иначе слепое восприятие стало бы лучше
зрячего.

**Единая система для трёх потребителей:**

| Потребитель | Текущее состояние | Отличие от целевого поведения |
|---|---|---|
| Огонёк на пальцах (Священник) | Флаг `bIsPeekActive` готов, физический огонёк горит, силуэты не рисуются вовсе | Полностью отсутствует |
| Mental Trail (Реднек) | Маркеры шагов есть, но визуально задавлены `EyesClosedPostProcessComp` с 27.08.2026 | Видимость сломана регрессией; дёргание/фантомы не реализованы в принципе |
| Чернильное зрение (Наездница) | `M_InkVision` — Stencil-силуэты + контур глубины + чернильные капли, рендерится | Нет «дёргания»/телепортации силуэта и фантомных образов по времени/углу |

Технический путь (намеченный в нескольких спецификациях, не выбран окончательно) —
Custom Depth/Stencil-рендер монстров поверх общего пост-процесса, единый материал,
разные цветовые тона на потребителя (тёплый огонёк Священника, чёрно-белые чернила
Наездницы, собственный тон Mental Trail/Брата).

**Открытые вопросы (решить при постановке ТЗ на имплементацию):**
- Параметры «дёргания»: частота подрагивания, интервал «перескока» в другую точку,
  максимальное отклонение от реальной позиции монстра.
- Условия появления/исчезновения фантомных образов: порог изменения угла обзора,
  таймер жизни фантома, вероятность появления ложного силуэта вообще без монстра
  поблизости.
- Применяется ли эффект одинаково для всех трёх потребителей, или степень
  неточности/частота дёргания — параметр, настраиваемый отдельно на герое (например,
  у Наездницы чернила давно выбраны как «второе дыхание» более высокого качества, чем
  Mental Trail Реднека).

## 9. Укрытие — спрятаться в предмет

Почему это нужно: закрытые глаза и персонажные техники снижают риск, но не убирают
его полностью (Eye Peek, Blind Encounter, ошибки тайминга). Укрытие — единственная
**гарантированная** безопасность, общая для всех героев без исключения.

**Механизм (`UHidingComponent`, клавиша E):**

```
E нажата, не спрятан
  → bIsTrapped / bIsPanicking / bIsAwaitingGetUp / IsMounted()? → no-op
  → ближайший свободный AHidingSpot в радиусе HidingSpotSearchRadius (200)?
      нет → no-op
      да  → EnterHidingSpot():
              - телепорт персонажа в точку укрытия
              - DisableMovement(), SetActorEnableCollision(false)
              - bIsHidden = true, Spot->SetOccupied(true)

E нажата, уже спрятан
  → ExitHidingSpot(): возврат на точку входа, коллизия/движение восстановлены,
    Spot->SetOccupied(false)
```

**Гарантия необнаружения:** пока `bIsHidden == true`,
`ABaseMonster::IsPlayerVisible()`/`IsPlayerLookingAtMonster()` безусловно возвращают
«не вижу» (см. `05-monsters.md` §6) — независимо от состояния глаз. Отключённая
коллизия капсулы также исключает физический слепой контакт (`OnCapsuleHit()` не может
сработать).

**Размер укрытия относительно персонажа** — заявлено пользователем как условие
(«если укрытие достаточно под размер персонажа»), но **не реализовано**: любой
`AHidingSpot` в радиусе поиска подходит любому герою без проверки совместимости (см.
§4). Параметры размера (например, минимальные габариты для крупного персонажа/Брата)
— определить при постановке ТЗ.

**Общий примитив для смежных механик:** `SetHiddenExternally()` позволяет другим
системам переиспользовать тот же `bIsHidden`/`IsHiddenInSpot()` путь без настоящего
`AHidingSpot` — так уже делает крюк Наездницы (`URiderHookComponent`,
`03-rider-character.md` §7.2) и предположительно будет делать «безопасное место
Сестры» (`04-brother-sibling.md` §9.1, открытый вопрос §12 п.10).

**Не реализовано (будущие задачи):** риск обнаружения/принудительного вскрытия
укрытия монстром; ограничение по размеру предмета/персонажа.

## 11. Раскладка клавиш (общие)

| Клавиша | Действие | Детали |
|---|---|---|
| **Shift** | Открыть/закрыть глаза (тоггл) | `ToggleEyesClosed()` |
| **ПКМ** (удержание) | Подглядывание/прицеливание (Eye Peek) | `StartAiming()`/`StopAiming()`, риск обнаружения в конусе монстра; принудительно выключено во время паники (§7.4) |
| **E** | Войти/выйти из укрытия | `OnHidingTogglePressed()` — также используется `Interact()`/`MashTrapEscape()` на том же герое, каждый сам проверяет применимость; не работает во время паники (§9) |
| **G** (в приседе) | Прощупывание пространства вслепую | `OnProbePressed()` → `UProbeComponent::Probe()`, см. §7.2 |
| **Space** (во время паники) | Дыхание носом в такт — мини-игра паники | `OnBreathPressed()`, см. §7.1 |
| **W** (во время паники, после выравнивания дыхания) | Встать после паники | `RecoverFromKnockdown()` через `Move()`/edge-triggered «вперёд», см. §7.1 |
| **H** | Показать/скрыть подсказку управления | Общая для всех героев |

Персонажные клавиши техник видения вслепую (F/V у Священника, V у Наездницы, ПКМ+ПКМ-
удержание у Реднека) перечислены в соответствующих спецификациях и не дублируются
здесь.
