### 1.1 Угроза от открытых глаз (фоновое правило для ЛЮБОГО монстра) — упрощённая версия
- **Проверено в коде (14.08.2026): сейчас видимость игрока монстром — это фиксированный радиус (`SightDistance`/`DetectionDistance`) + бинарная проверка `IsEyesClosed()`, без масштабирования дистанции. Полной системы видимости в коде нет.** Решено: 1.1 делаем на этом бинарном гейте как есть, дистанцию не трогаем. Полная система видимости (см. 1.1b ниже) — отдельная задача позже.
- Открытые глаза в поле зрения монстра = сигнал к атаке.
- Монстр издаёт зов (уже есть `BroadcastAlert`) → переходит в Chase (уже есть) → добегает → издаёт ВТОРОЙ зов прямо перед ударом, созывая других монстров рядом (они тоже подбегают и бьют) → атакует.
- Если игрок вовремя приседает — избегает удара (по аналогии с уже существующим crouch-dodge в `DoesEyePeekAttackConnect`).
- **После успешного уклонения монстр НЕ должен сразу возвращаться к обычному Patrol/Chase** — какое-то время должен оставаться раздражённым/сканирующим (переиспользовать существующее состояние Scanning/`EnterScanningState`, а не изобретать новое).
- Если не присел — стан на полу → начинается паника/дыхание (уже есть `EnterPanicState`).
- **Уточнение (14.08.2026): глаза принудительно открываются не от пропуска дыхания, а когда шкала паники доходит до верха — это уже реализовано и работает корректно, трогать эту логику не нужно.** Единственное, чего не хватает: когда `ForceEyesOpenFromPanic` срабатывает и рядом в этот момент есть монстр — должна наступать смерть (сейчас этого следствия нет).
- **Это же правило действует и в самом стане напрямую**: открыл глаза в упор перед монстром, будучи в стане — смерть, независимо от исхода дыхания/шкалы.
- Задача: связать существующие примитивы (`BroadcastAlert`, Chase, `EnterPanicState`, `ForceEyesOpenFromPanic`, crouch-dodge паттерн, `EnterScanningState`) в фоновую проверку, которая работает для ЛЮБОГО монстра в обычном Patrol/Chase, а не только внутри спец-сценариев Eye Peek/Blind Encounter.

### 1.1b Полная система видимости (ОТДЕЛЬНАЯ задача, после упрощённой 1.1) — НЕ начато, строить с нуля
- Задумка: видимость игрока — это не только глаза, а комбинация факторов: тёмная одежда, лицо в саже, закрытые глаза (глаза — самый сильный маркер). Открытое/незакопчённое лицо и одежда не тёмного цвета — повышают видимость. Все три фактора вместе (тёмная одежда + сажа + закрытые глаза) = полная защита/неразличимость.
- По задумке это должно влиять на ДИСТАНЦИЮ, с которой монстр вообще замечает игрока (масштабировать `SightDistance`/`DetectionDistance`), а не быть ещё одним бинарным гейтом.
- **В коде сейчас нет вообще ничего**: ни состояния «тёмная одежда»/«лицо в саже» у персонажа, ни VisibilityScore, ни масштабирования дистанции обнаружения — подтверждено проверкой кода.
- **Открытый вопрос: как игрок получает тёмную одежду/сажу на лице (предмет? действие? фиксировано по герою?) — пользователь отложила решение («потом сделаем»).** Не начинать эту задачу, пока это не решено.
- **Решено (15.08.2026): «Чернильные капли» (закапывание в глаза) — эксклюзивный аварийный предмет Наездницы, не общий для всех героев.** Источник — ранние наброски GDD (`_Game Design Document_.docx`, не золотой стандарт), где чернила изначально были у всех троих видимых героев (Реднек/Священник/Наездница), каждому со своей обёрткой. Пользователь пересмотрела: Реднек и Священник уже имеют собственный способ ориентироваться без открытых глаз — Реднек через Охотничий глазомер (`UHunterFocusComponent`, подглядывание+просчёт шагов), Священник через видение силуэтов сквозь веки по огоньку на пальцах (в коде пока не реализовано отдельно, только сама Holy Item свеча). Чернила для них были бы дублирующим инструментом, поэтому предмет остаётся только у Наездницы («Второе дыхание» — используется, если кадило погасло или её сбило с монстра). В коде по-прежнему ничего не реализовано (см. пункт выше) — эта заметка только фиксирует, ЧЕЙ это будет предмет, когда до реализации дойдёт очередь.
- **Уточнение механики капель (15.08.2026, пользователь).** Капли красят глаза в чёрный — персонаж физически ходит с открытыми глазами (видит мир в ч/б, только очертания), но для монстров/системы обнаружения это **считывается как закрытые глаза** (`IsEyesClosed()` эффективно остаётся `true`, либо отдельный флаг, который в формуле видимости 1.1b весит так же, как закрытые глаза, — решить при реализации, что технически проще). Эффект временный (таймер, длительность не определена). Из этого следует ответ на вопрос выше про формулу видимости: капли — это НЕ отдельное самостоятельное слагаемое видимости, они просто позволяют держать «глаза закрыты» (с точки зрения монстра) и одновременно не быть слепым — весь их вклад в видимость уже покрывается фактором «закрытые глаза», ничего сверху добавлять не нужно. Открытым остаётся только сам сенсорный эффект для игрока (ч/б, очертания) — отдельная задача на реализацию (пост-процесс), не связана с формулой видимости монстра.
- **Решено (16.08.2026, пользователь): силуэтный пост-процесс для чернил и для «Огонька на пальцах» (Приест, см. Фазу 4 п.10, СДЕЛАНО в коде+физический свет, но не в рендере) — ОДНА общая реализация, разное цветовое решение.** Оба эффекта функционально одинаковы (временное зрение силуэтами без реальной видимости для монстров), поэтому не дублировать пост-процесс-материал/эффект дважды — сделать один настраиваемый по цвету, когда дойдёт очередь: чёрно-белый (десатурированный) тон для чернил Наездницы, тёплый красновато-оранжевый (цвет пламени — тот же оттенок `FLinearColor(1.0, 0.45, 0.15)`, что уже используется физическим светом `APriestCharacter::FingerFlameLight`) для огонька Священника. В коде сам пост-процесс по-прежнему НЕ реализован ни для одного из двух — эта заметка фиксирует только цветовое решение на будущее.
- **Третий потребитель той же нерешённой задачи, найден по факту регрессии (27.08.2026)**: Mental Trail Реднека (`UHunterFocusComponent::MentalTrailColor`, обычный полупрозрачный материал в мире) перестал быть виден с закрытыми глазами после усиления `EyesClosedPostProcessComp`'s темноты — новая тонировка/экспозиция давит весь кадр одинаково, маркеры больше не пробиваются. По решению пользователя — НЕ патчить точечно (поднятием яркости материала — обсуждали, сработало бы физически, но непредсказуемо без подбора в PIE и потребовало бы поднимать яркость на порядки из-за `AutoExposureBias`), а решить один раз через общую систему «видно сквозь слепоту»: Custom Depth/Stencil + Post Process материал, рисующий целевые объекты поверх готового кадра независимо от `EyesClosedPostProcessComp`. Когда дойдёт очередь до этой задачи — она закрывает СРАЗУ три вещи: чернильные капли, огонёк на пальцах, и возвращает Mental Trail в рабочее состояние. Подробности регрессии — `CLAUDE.md`, строка «Охотничий глазомер (+ Mental Trail)».

### 1.2 Угроза от физического наскока (фоновое правило) — **уточнено пользователем 14.08.2026, старое описание было неточным**

- Наскок на монстра (бег/ходьба/прыжок в него) → монстр СРАЗУ бьёт в сторону игрока — это не просто «раздражается и сканирует», первый физический контакт сам по себе запускает попытку удара, по той же схеме crouch-dodge, что уже есть у Eye Peek/Chase-атаки (Фаза 1.1):
  - Не успел присесть → удар засчитывается → паника (как в 1.1).
  - Успел присесть → монстр промахивается, но остаётся раздражён и ещё какое-то время сканирует территорию (переиспользовать Scanning/`EnterScanningState`, как и раньше планировалось).
- Чтобы монстр успокоился во время раздражения/сканирования: игрок должен либо отступить, либо присесть — **и присесть нужно ТОЖЕ с закрытыми глазами** (одного приседа недостаточно). Просто замереть с закрытыми глазами, НЕ приседая, не спасает — паника всё равно наступит, если монстр достанет ударом.
- **Новая механика (нужна для этого пункта, раньше не было в задаче)**: функция «красться» (sneak/stealth-движение) — без неё аккуратное отступление всё равно раздражает монстра до удара. С активной «крадущейся» походкой монстр может ненадолго настораживаться/останавливаться, но не бить. Это ОТДЕЛЬНАЯ новая механика, не просто переиспользование существующих примитивов — по правилам изоляции механик в `CLAUDE.md` ей нужен свой компонент (например, состояние движения на `ABaseCharacter` или отдельный `UStealthComponent` — решить при постановке ТЗ), а не логика внутри уже существующих. Имеет смысл разбить 1.2 на 1.2a (наскок/раздражение/сканирование — по образцу 1.1) и 1.2b (сама механика «красться») как отдельные задачи.
- Если контакт повторяется, пока монстр раздражён — стан + зов другим монстрам (та же цепочка, что в 1.1) — **но зов должен звучать, только если монстр ТОЧНО поймал/застанил игрока** (успешный удар/стан), а не при любом повторном контакте или очередном промахе.
- Задача: обобщить существующий Blind Encounter/Scanning как фоновое поведение любого монстра, с таймером раздражения/остывания + отдельной задачей добавить механику «крадущегося» движения (см. выше).

**✅ 1.2a — СДЕЛАНО, основной цикл подтверждён в PIE (14.08.2026).** Первый наскок с открытыми глазами → удар/уворот (crouch-dodge, как в 1.1); промах → раздражённое сканирование без зова; повторный контакт во время сканирования → мгновенный урон+паника+зов без второго шанса увернуться; зов звучит только на подтверждённом попадании. Реализовано через `TryStartNaskokAttack()`/`PendingNaskokAttackTarget` — третий независимый источник, параллельный Eye Peek и Chase-атаке, переиспользует всю их инфраструктуру. Все 5 automation-тестов зелёные. Подробности — `CLAUDE.md`, строка «Наскок (Фаза 1.2a)».

**✅ 1.2b — «красться» — ПЕРЕОСМЫСЛЕНО и СДЕЛАНО иначе, чем описано выше (16.08.2026), стабильно, полностью подтверждено в PIE.** При постановке задачи выяснилось, что описание выше устарело: (а) проверка кода показала, что Scanning-состояние и так уже полностью замораживает `Tick()`/`CheckForPlayer()` монстра (никакого нового обнаружения не происходит, пока идёт `ScanDuration`) — единственная реальная опасность отступления это ФИЗИЧЕСКИЙ повторный контакт капсулы (уже наказывается существующей веткой `TryStartNaskokAttack()`); отдельная проверка «присесть+закрыть глаза чтобы успокоить монстра раньше таймера» в коде никогда не была реализована — эта старая формулировка снята с повестки; (б) пользователь при постановке задачи раскрыла куда более широкий замысел «красться»: игра рассчитана на игру в ПОЛНОЙ темноте — игрок физически не видит монстров на экране, только слышит. 16. **Sun Exposure / бегство в тень — ПОДТВЕРЖДЕНО, работает по задумке.** Проверено вручную: на открытом пространстве монстры разбегаются к укрытиям (здания и т.п.), на закрытом — в буквальную тень; сгорание при реальном отсутствии укрытия — валидный игровой исход, не баг. Не трогать без явной причины. На будущее — держать в поле зрения ретрай-циклы поиска точки тени в коде (комментарии в `BaseMonster.cpp` про «wander point search FAILED — retrying») на случай проблем на более сложной геометрии уровня, чем текущая тестовая арена.
17. Реакция на шум — не нужна для Уровня 1, отложено.
18. **Потолочный монстр** (идея зафиксирована 26.08.2026, дизайн детально проработан 02.09.2026 в разговоре с Claude, КОД НЕ НАЧАТ — жёстко зависит от Фазы 7 пп.19-20, см. ниже). Отдельная разновидность монстра, живущая на потолке/стенах и атакующая сверху — впервые всплыла при проектировании крючков Наездницы (Фаза 5, «Крючки») как естественное продолжение вертикальной угрозы.

    **Детекция — принципиально другая, чем у всех остальных монстров**: видит игрока при любом состоянии глаз (открыты/закрыты), если тот просто попадает в его поле зрения — не участвует в общем правиле «слепой = невидимый» (Фаза 1.1). Единственное исключение — Брат, пока он в форме монстра (Фаза 7, п.19): для этого монстра Брат-трансформация не читается как цель, хотя рядовые монстры вообще не атакуют трансформированного Брата (он для них «свой») — этот монстр как раз единственное исключение из ИСКЛЮЧЕНИЯ, он продолжает видеть Брата как угрозу независимо от формы. Отсюда жёсткая зависимость: без готовой трансформации Брата не на чем строить проверку безопасности, поэтому пункт остаётся не начатым, пока Фаза 7 пп.19-20 не реализованы.

    **Спасение — только укрытие.** Переиспользуем стабильный `UHidingComponent`/`AHidingSpot` (Фаза 2, «Укрытия»). У монстра нет здоровья, убить нельзя (даже Наезднице) — единственное воздействие на него — отбрасывание (`ApplyKnockback()`, по образцу уже существующих мест). Наказание при поимке: удар отбрасывает игрока далеко в сторону и в этот же момент зовёт подмогу (`BroadcastAlert()`) — сам отброс работает как окно на побег/поиск укрытия, а не как чистое наказание. Повторная поимка (монстром или подоспевшей подмогой) ДО того, как игрок спрятался — критический урон (ориентир — сразу половина здоровья, точная цифра по балансу в PIE).

    **Движение.** По умолчанию монстр на потолке/стенах, смотрит на уровень сверху вниз; по полу передвигается не ходьбой, а отдельными прыжками. Может допрыгнуть до Наездницы даже на потолке и спрыгнуть с потолка прямо на игрока (атака-прыжок). Техника навигации по трём типам поверхностей НЕ выбрана — варианты от простого к сложному: (а) кратчайший путь к цели + переориентация по нормали ближайшей поверхности; (б) движение только по заранее расставленным дизайнером точкам/сплайнам; (в) полноценная процедурная навигация по произвольным поверхностям пол/стена/потолок. Решение отложено до прототипа — по ощущениям пользователя, скорее всего понадобится (в), но не финально.

    **Появление — две независимые системы триггера параллельно**: заранее расставленные дизайнером точки принудительного появления (для конкретных сценарных моментов) и отдельно рандомный механизм появления в подходящих местах без ручной расстановки (для непредсказуемости). Перед появлением — нарастающий звук, дающий честное окно на поиск укрытия (телеграфирование, не мгновенный джампскейр без предупреждения).

    Сознательно отложено: сначала нужно закрепить и обкатать в PIE уже реализованный основной геймплей (герои, укрытия, крючки, капканы и т.д.) и довести до готовности Фазу 7, и только потом браться за этот тип монстра.

## Фаза 7 — Брат и Сестра (низкий приоритет — после всех остальных героев)

**Полный дизайн зафиксирован 02.09.2026 (разговор с Claude), КОД НЕ НАЧАТ.** Управление — без ручного переключения по кнопке: смена активного персонажа происходит только автоматически, в заскриптованных точках сюжета. Пока ведём одного, второй существует в фоновом/пассивном состоянии (см. п.21) — например, Сестра с мешком на голове едет на спине у Брата, тикая своим таймером, пока играем за него; в нужной точке управление переключается на Сестру, а Брат ждёт на месте, пока не доиграем её отрезок (и наоборот).

18. Два отдельных актора: `ABrotherCharacter` + `ASiblingCharacter` (`Sibling` = имя класса Сестры). Переключение между ними ТОЛЬКО автоматическое, по сюжетным точкам — свободного ручного переключения нет.

19. Трансформация Брата в монстра — ОТДЕЛЬНАЯ форма на самом `ABrotherCharacter` (свой набор атак/коллизий), **не превращение в `ABaseMonster`** — осознанное архитектурное решение, чтобы не тащить в этот класс весь груз ИИ-состояний монстра. Детали 02.09.2026:
    - Зрение в темноте в этой форме — вариант уже готовой системы Чернильного зрения Наездницы (тот же принцип: контур силуэтов + подсветка монстров через Custom Depth Stencil), возможно другим цветом/тоном — это его собственная звериная природа, а не наведённая магия предмета. Бо́льшая часть шейдерной работы уже сделана для Наездницы, адаптировать проще, чем строить с нуля.
    - Рядовые монстры НЕ атакуют трансформированного Брата — он для них «свой», не добыча. Единственная опасность для него в этой форме — собственная шкала Заражения (п.20), не чужие зубы, поэтому отдельная защита/атака ему не нужна.
    - Новая способность в форме — звук-приманка: привлекает рядовых монстров в радиусе к себе, освобождая путь Сестре. НЕ действует на Потолочного монстра (Фаза 6, п.18) — тот единственный, кто продолжает видеть Брата как угрозу независимо от формы.

20. Шкала Заражения растёт за время, проведённое в форме монстра за один раз. Детали 02.09.2026:
    - «Безопасный» грейс-период в начале каждой трансформации, пока шкала не растёт; после его истечения шкала начинает расти, пока Брат остаётся в форме.
    - У Брата свой таймер отдыха в укрытии — короче, чем у Сестры, отсидеться так же долго он не может.
    - **Жёсткий порядок действий**: если безопасное время Брата кончилось, а у Сестры своё ещё есть — он ОБЯЗАН сначала спрятать Сестру и только потом искать укрытие себе. Спрячется сам, оставив её снаружи — она паникует и срывает мешок сама (тот же летальный исход, что в п.21).
    - При 100% — Брат убивает Сестру, game over. Подтверждено пользователем (02.09.2026), без исключений, если не успел спрятать её вовремя.
    - Предупреждение: последние ~5% шкалы (число по балансу) мигают красным; при каждой трансформации Брат произносит тревожную реплику (ориентир — «это опасно, оно поглощает меня», финальный текст при озвучке) — завязано на будущую диалоговую/барковую систему (п.23).
    - Обычным геймплеем шкалу не откатить — весь смысл цикла в том, чтобы НЕ довести её до 100%, управляя ритмом периодических укрытий, а не «чинить» шкалу. Исключение — редкое зелье отката на несколько процентов: одна бесплатная порция в начале игры (дать почувствовать, как это работает), дальше полностью убрано из обычного лута до конца игры, и снова доступно ближе к финалу как награда за сайд-квест.

21. Перенос Сестры Братом (мешок на голове): медленнее движение, недоступны часть действий (присесть/спринт), Сестра недоступна для переключения, пока её несут. Детали 02.09.2026:
    - У Сестры свой таймер «мешка» (ориентир — около минуты, финальная цифра по балансу в PIE): последние ~10 секунд — мигание красным как предупреждение; по истечении — паника, срывает мешок сама, открывает глаза → мгновенная смерть (тот же летальный путь, что Blind Encounter, просто новый триггер).
    - Успела до укрытия ДО истечения таймера — всегда безопасно стягивает мешок сама, дальше отдельный таймер восстановления медленно откатывает её «запас времени в мешке» обратно к полному значению (ориентировочно та же длительность, уточним в PIE).
    - Приоритет при укрытии — см. п.20 («сначала её, потом себя»).

22. Узкие щели/вентиляция Сестры — способ технического определения ещё не решён (открытый вопрос, решить перед началом реализации). Уточнение 02.09.2026: Потолочный монстр (Фаза 6, п.18) МОЖЕТ преследовать Сестру и в вентиляции — это не автоматически безопасная зона, а отдельное напряжённое пространство, где по-прежнему нужно прятаться.

23. Маскировка в баре, диалоговая система выбора реплик, ветвление на секретного героя, финал с последствиями — из ЛДД Акты IV-VI, привязаны к этому же блоку.

24. **НОВОЕ (02.09.2026) — способность Сестры «красться и петь».** Пока Сестра в состоянии «крадётся» (медленное движение) и монстр стоит к ней спиной (не видит её), она может запеть — монстр замирает на время действия способности (свой таймер длительности, число по балансу). Прерывание:
    - Переход на бег или выход из «крадётся» — пение прерывается автоматически.
    - Монстр её увидел — пение немедленно прерывается, монстр реагирует звуком «засёк» и идёт в погоню как обычно (обычная детекция, без послаблений).
    - После любого прерывания — кулдаун перед следующим пением.
    - Двойное назначение: та же способность помогает и Брату — Сестра из укрытия поёт по его команде, пока он в человеческом облике возится с препятствием (например, дверью) — переиспользование одной способности в разных сценах, не отдельная механика.

25. **НОВОЕ (02.09.2026) — обход деревни.** Сестра свободно проходит через деревни/зоны с NPC, Брат — нет (по мере превращения его туда не пускают/реагируют негативно). Сестре нужно находить обходные пути, чтобы провести Брата в обход таких зон. Открытый вопрос — как именно NPC «не пускают» Брата (визуальный барьер, скриптованный отказ, полноценная система подозрения/тревоги) — решить отдельно перед реализацией, вероятно вместе с диалоговой системой п.23.
